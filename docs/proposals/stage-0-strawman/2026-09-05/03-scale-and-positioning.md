# 讨论稿：量级与定位重审 —— 虚拟化的真实价值与「小而美」档位

> 时间：2026-09-05。性质：**讨论稿，待所有者决策**——重开 `../2026-09-04/02-direction.md` 的 **D-2（量级 = 万~十万行 → DOM+虚拟化）**；D-1（业务列表表格）、D-3（编辑+undo）不受影响，本文不直接修改 ADR。
> 触发：所有者的需求侧质疑——真实业务用户几乎不连续滚动大结果集（过滤/查询/分页才是习惯，Navicat 一页最多 1000 行），怀疑虚拟化是「技术驱动」而非「用户驱动」；倾向「小而美」档位（百~千行），信条「要么做到极致，要么不做」。
> 证据基线：`spike/2026-09-05-grid-demo/RESULTS.md`（下称「DOM spike」；含 2026-09-05 增补的「5000 行拖拽复核」小节）、`spike/2026-09-05-fullrender-demo/RESULTS.md`（下称「fullrender spike」——§3 工程化主张的实测来源）、`spike/2026-09-05-canvas-demo/RESULTS.md`（下称「canvas spike」）、`../2026-09-04/01-market-research.md`（下称「调研」）、同目录 `01-typescript-types-research.md`（下称「类型调研」）。

## 0. 结论速览

1. **虚拟化买到的只有一件事**：渲染 DOM 从 O(行数) 降到 O(视口)。它不是「大数据量」方案——大数据量分三层（传输/内存/渲染），传输用分页、内存用窗口查询就能解决，虚拟化只管渲染层，且仅当用户**在同一个列表里连续滚动浏览**时才被需要（§1）。
2. **两份 spike 最难的教训全是虚拟化税**：滚动形态二分、跳转检测、lead buffer、行回收、合成器领先、a11y 乱序。方向文档决策表 12 条中 4 条（#2/#3/#10/#12）是纯虚拟化约束。「坑好大」的直觉有实证（§1.2）。
3. **真需要十万行连续滚动的场景存在，但不在我们客群**：交易终端、日志/可观测、DevTools、电子表格、科学数据检视——共同判据是「滚动即交互 + 专业扫描者 + 小时级时长」。中后台 CRUD 用户是任务完成者，同类工具行业全部用分页。所有者的判断成立（§2）。
4. **拖拽白屏由速度阈值决定，不由总高单独决定**（回应追问；2026-09-05 screencast 实测修正，撤回初版「5000 行连拍满行」结论——那是停顿截图假阴性）：5000 行下慢拖（≲30 行/步）拖拽中满行；快拖/极速（≳57 行/步）拖拽期间表体 ~100% 白（虚拟化/全量 × cv0/cv1 四组皆同），松手 ≤600ms 追平。总高的作用 = 把同一手部速度映射成更大的每帧位移（10 万行 8px 手势 ≈ 1000 行/步，几乎全部拖速在界外；5000 行同手势 57 行/步，恰好压线）。「虚拟化在自己不痛的区间里本就不被需要」依然成立且更干净——它的窗口机制只解决 JS 层，上屏层的光栅化追赶两档同物理，本就不构成档间差异（§3.2）。
5. **小而美 ≠ 缩水版大表**：全量渲染档删掉整套虚拟化机器，换来虚拟化档没有的物理红利——Ctrl+F、a11y 自然序、打印、**autoHeight 回归**（初版列首位的「任意速度零白屏」已按 screencast 实测撤回：快拖及以上两档同样拖拽期间整屏白，见 §3.2/§3.3）；core 层 100% 幸存（spike 已证渲染器可替换，`diff -r` 零 core 改动）（§3）。**已建 demo 实测**（`spike/2026-09-05-fullrender-demo/`）：首块 200 行 13-19ms、5000 行同步全量 242ms（0.053ms/行）；c-v 收益挂载墙钟 3.6-4.6× / 极限拖拽主线程 2.1×；**编辑成本是真正的坑**（5000×20 一次编辑冻结 1.2s，需 per-row 分片，§3.1）。
6. **该档位性能是卫生因素，不是卖点**：差异化在 TS 类型体验、键盘/a11y、包体/树摇/零依赖、API 稳定——恰是类型调研的主轴。市场对照：无虚拟化全量渲染本就是主流业务表格的默认档，此定位不激进（§4）。
7. **核心待决策**：虚拟化去留三选项——(a) 进非目标、架构留缝（本文推荐）；(b) 双档产品；(c) 维持 D-2（§5.3、§7）。

## 1. 虚拟化买什么、付什么（机制层）

### 1.1 大数据量有三层，虚拟化只管一层

| 层 | 问题 | 解法 | 与虚拟化的关系 |
|---|---|---|---|
| 传输/获取 | 几十万行怎么到浏览器 | 服务端分页、窗口查询（offset/keyset） | 无关。Navicat 1000 行/页、DBeaver 默认 200 行/批，解决的就是这层 |
| 内存/状态 | 数据驻留哪 | 全量行数组（DOM spike 直接生成 10 万行×20 列 mock，430-600ms，完全可行） | 无关。持有数据 ≠ 要渲染数据 |
| 渲染 | DOM 节点数 = 行×列 | 分页（换页重渲）、虚拟化（同一列表内窗口化） | **只有这层**。虚拟化把常驻 DOM 从 O(n) 压到 O(viewport) |

**推论：「数据多」不必然「虚拟化」。** 数据多到传输/内存层，分页与查询就是正解；虚拟化只回答一个问题——**用户要不要在同一个滚动列表里连续浏览超过屏幕能舒适渲染的行数**。这不是性能问题，是交互形态问题。

### 1.2 代价清单：不是代码量，是约束与 bug 面

全部来自两份 spike 的一手实证（非推测）：

| 代价 | 实证 |
|---|---|
| 滚动形态二分 | 连续（滚轮/触控板）与不连续（拖滚动条/跳转）是两个世界，测试与实现都要双份（DOM spike 教训 1） |
| 一整套滚动状态机 | 速度感知 lead buffer（封顶 90 行是白屏消除门槛）、跳转检测（阈值 = 窗口行数×行高）、batch 防中间态 |
| 行回收池 | mount 0.45ms/行 不达标 → 差分规划器 + 池 + rowIdAtom，rebind 0.006ms/行（~73×）才跨过吞吐墙 |
| 合成器领先 | 拖原生滚动条主线程结构性落后 ≥1 帧；限速钳制实测否决（取消拖拽手势 + wheel 59.8→13.1fps）；只能骨架/lead 缓解 |
| 状态协商复杂度 | 键盘导航×虚拟化（决策 #10）、树形展开锚点补偿、CSSOM 序列化有损、store 顺序 set 中间态 |
| a11y 降级 | cell 无 aria 属性、rebind 后 DOM 序 ≠ 逻辑行序，需 aria-rowindex 同步（DOM spike 已知简化 2） |
| 产品级约束 | autoHeight 互斥（#12）、行高三档管理（#3）、列虚拟化后置（#2）——全是「因为虚拟化所以不能」 |

### 1.3 小结

虚拟化是「滚动即交互」场景的**专用件**，不是表格的**默认件**。把它设为默认档，等于让所有用户为少数场景预付全部约束与 bug 面。

## 2. 谁真的在滚十万行（场景调研）

### 2.1 真·需要连续滚动的场景（存在，画像清晰）

| 场景 | 为什么过滤替代不了滚动 | 用户 |
|---|---|---|
| 金融交易终端 blotter（AG Grid 核心付费客群） | 实时成交流/持仓的顺序扫视，过滤后丢上下文 | 交易员 |
| 日志/APM/可观测（Datadog/Splunk 类 trace 查看器） | 时间序连续流，滚动即浏览 | SRE/运维 |
| DevTools（Chrome Network/Performance、VS Code 搜索结果） | 顺序即因果/相关性 | 工程师 |
| 电子表格（Excel/Univer：网格本身就是 100 万行） | 网格即文档 | 所有用户（D-1 已排除此形态） |
| 科学数据检视（基因组浏览器 IGV 等） | 坐标连续性 | 研究人员 |
| 大列表（文件管理器、媒体库） | 浏览式消费 | 消费者 |

**共同判据三条**：① 滚动本身是核心交互（顺序扫视，过滤不能替代）；② 用户是专业扫描者（交易员/SRE/分析师），扫视是职业技能；③ 单次会话小时级。

### 2.2 反例阵营：中后台 CRUD（我们的客群）

用户是**任务完成者**：查 → 过滤 → 定位 → 处理，滚动深度天然浅。行业事实：Navicat 1000 行/页、DBeaver 默认 200 行/批、Grafana 表格面板分页、Salesforce/Jira 列表分页——**没有一个主流业务工具把「连续滚十万行」当交互模型**。

调研里的性能口径（AG Grid Client-Side 10 万+、Handsontable 1 万~10 万）是**能力上限口径**，不是需求口径。「几十万行不过滤直接滚」的用户不存在——真要看全量的人，用的是导出 Excel。（对账/盘点类「扫视」任务确实存在，但用户的解法同样是导出，不是在浏览器里滚。）

**判定：公司 Vue3 中后台属于反例阵营。虚拟化对目标客群是技术驱动，不是用户驱动。**

## 3. 「小而美」档位的技术可行性

### 3.1 全量渲染的成本与工程化

成本底数（已实测修正，fullrender demo，生产构建）：1000 行×20 列 ≈ 2.3 万 DOM 节点。**0.45ms/行是 grid-demo Vue v-for mount 时代的数字**；复用已建资产（命令式 buildRow + 列样式静态化 + 事件委托）后裸渲染 = **0.053ms/行**（8.5× 便宜）——1000 行同步全量 **~60ms / 242ms@5000 行**，分块首屏后首块 200 行 **13-19ms**。原「1000 行 ≈ 0.5s 不达标」的判断只适用于组件粒度渲染路径，不适用于资产复用后的命令式路径（Element Plus 1k 行的卡顿正是前者；调研 §5 的 shallowRef 优化案例「渲染耗时降 85%」反证的也是组件路径之慢）。

工程化三件套（都不引入虚拟化的状态机；均已实测）：

1. **分块渐进首屏**：先渲 200 行可交互，rAF 分块补齐。无状态、无滚动耦合。实测：**首块 13-19ms 与总行数无关**（1000/5000/10000 行同值）；5000 行全量墙钟 944ms（滚动条在数据就绪时即达最终长度，分块期间不跳变）。
2. **`content-visibility: auto` + `contain-intrinsic-size`**：浏览器原生跳过屏外渲染（paint/layout 级），**DOM 保留**——Ctrl+F、a11y、打印全部不破。Chrome 85+/Firefox 125+/Safari 18+，2026 年基线安全。实测收益：**挂载墙钟 5000 行 3408→944ms（3.6×）、10000 行 10794→2319ms（4.6×）**；极限拖拽主线程 fps 16.7→35.7（2.1×，屏外行样式/布局不再随滚动重算）；paint-hold 副作用待重证（初版「未观察到、连拍满行」出自停顿截图、不足为凭；可站住的旁证 = cv0 快拖同样整屏白，白屏与 c-v 无关）。**从「兜底手段」升为默认必开。**
3. **已建资产直接复用**：列样式静态化、事件委托 + 几何命中（DOM spike 为虚拟化档所建，全量档同样受益）、cell 级 === diff（数据层，与渲染档无关）。实测：交互语义 11 项全过（编辑 `__cellRenders` 恰 +1、锚点补偿、订阅恒等式），core 数据层 0 改动——「渲染器可替换」第三个数据点（DOM 虚拟化 / canvas / DOM 全量同 core）。

诚实的代价（实测后重排大小序，fullrender RESULTS）：

- **编辑扩散（真正的头号坑）**：dataVersion bump 重跑全部常驻 cell effect，O(挂载 cell) 随行数线性乃至超线性——单次编辑/undo：1000 行 58-75ms、5000 行 **1182ms**、10000 行 4404-4572ms。修法方向 = per-row dataVersion 分片/脏行集（O(挂载 cell) → O(变更行×20)），**5000 行档位承诺必须以分片为前提**。
- 一次性 mount 成本：已被三件套压到次要（首块 13-19ms；全量墙钟靠 c-v）。
- 常驻内存：5000×20 ≈ 10.5 万 DOM 节点 + 9.16 万常驻 effect（「用空间换 JS 层无未挂载区」的账；上屏层白屏两档同物理、没换到，见 §3.2；grid-demo 同规模仅 ~5k 节点）。
- 排序/筛选全量 diff：cell 级 === 使其有界，千行尺度远低于帧预算（未变）。

**档位语义（按维度拆开说，实测后）**：滚动维度——甜点 ≤500 行一流，**~5000 行可用已实测**（慢拖满行、快甩拖拽期间白+松手 ≤600ms 追平——与虚拟化档 5000 行白法相同；wheel 49-51fps）；编辑维度——甜点 ≤500 行（~30ms）良好、~1000 行（60-75ms）勉强、**≥5000 行需先做 per-row 分片**。超出引导分页/导出。**软性能包线 + dev 警告，不做硬上限**——硬上限只会激怒把 6000 行塞进来的用户；软包线 + 文档承诺 + dev 警告才是诚实工程。

### 3.2 量级 × 拖拽白屏边界（回应追问：只有 5000 行，不连续拖拽还白屏吗）

白屏有两层来源，只有第二层的触发阈值跟总高有（间接）关系——2026-09-05 screencast 复测后分层修正：

| 白屏层 | 与总行数的关系 | 5000 行下的状态（screencast 实测） |
|---|---|---|
| ① JS 挂载/更新吞吐（DOM 层） | **无关**（取决于每帧需挂行数与单行成本） | 行回收已根治：rebind 0.006ms/行，跳转分流只挂可见窗口（~120 行）< 1ms/帧；快拖档 mounts=0、rebinds 2472、assignMs 19.9——DOM 恒满（采样 0/513） |
| ② 上屏层：合成器先行 + 新暴露区瓦片未光栅化 | 机制无关（普遍物理）；**触发阈值 = 每帧新暴露 ~1000-2000px（实测边界落在 30-60 行/步之间）**，总高只通过「同一手势 → 更大位移」的映射间接影响 | 慢拖 ≲30 行/步：**满行**；快拖 ≳57 行/步：拖拽期间表体 ~100% 白（表头恒画、pinned 列体空、连背景层都不画）；松手 ≤600ms 追平。虚拟化/全量 × cv0/cv1 四组同证 |

拖拽位移对照（10 万行 = DOM spike 真机实测；5000 行推算列 = 按同一映射的纸面值；实测列 = 2026-09-05 复核，见 grid-demo RESULTS「5000 行拖拽复核」小节）：

| | 10 万行（350 万 px） | 5000 行（推算，初版） | 5000 行（screencast 实测） |
|---|---|---|---|
| 拇指 1px ≈ | 122 行 | ~6 行（线性估计） | **7.3 行**——拇指被系统最小长度 ~28px 兜底，实际映射 257px/px 略陡于线性 |
| 快拖 8px/10ms → 每帧位移 | ~1000 行 | ~~~78 行 < lead 封顶 90 行：落入「连续滚动」形态，presented 帧满行~~（DOM 层判定对；「presented 满行」错——上屏另有光栅化边界） | **57 行/步**：DOM 层连续形态成立（rebind 即时覆盖、mounts=0、采样 0/513）✓，**但上屏 ~100% 白**（cast 早/中/晚段帧） |
| 极限拖 32px/10ms → 每帧位移 | P50 ~4400 行（任何 lead 追不上 → 持续 ~60% 视口空白带，结构性） | ~~~310 行/帧：追赶 rebind <1ms → 残留约 1 帧瞬态~~（「1 帧瞬态」低估——白持续整个拖拽期） | **227 行/步（忙帧合批更高）**：跳转判定跨阈值、JS 即时覆盖 ✓，**上屏同样 ~100% 白**（连骨架条纹背景都未上屏） |
| 感知 | 极限拖拽明显空白 | ~~常规拖拽无感，极限速度下 1 帧过渡~~ | **实测（作者手感反馈 + cast 证实）：快甩及以上拖拽期间整屏白、松手即满；慢拖满行** |

**临界线（修正后）**：① JS 层——每帧位移跌破挂载窗口（视口+lead ≈ 130 行）时「不连续拖拽」退化为「连续滚动」，DOM 层白屏消失（已实测：5000 行 fast 57 行/步，rebind 即时覆盖、mounts=0）；② 上屏层——独立的光栅化吞吐边界（实测落在 30-60 行/步之间，即每帧新暴露 ~1000-2000px）：快拖越界则拖拽期间表体白、松手 ≤600ms 追平，与渲染档、c-v 无关。初版的「N ≤ ~2000 画满的层 → 白屏物理上无从发生（任意速度）」**已被 5000 行全量档证伪**——无未挂载区照样白（白的是瓦片未光栅化，不是行未挂载）；更小的 N 因轨道短、同手势位移小，大概率整体落在边界内，但未单独实测，不再作为主张。Cmd+End 单跳零空白的机理不受影响（单跳后静止，追平在 ≤600ms 内完成，非持续拖拽形态）。

**推论（修正）：拖拽白屏是速度现象，不是架构现象。** 虚拟化档与全量档在 5000 行白法相同（同边界 30-60 行/步、同松手即满、cv 无关）——「零白屏」本就不构成两档的差异化维度（初版以为构成，是被停顿截图误导）；虚拟化真正的差异化只剩 JS 层吞吐与常驻 DOM 规模。「在 N 小到 JS 层不痛的区间里，虚拟化本就不被需要」的论证不受本次证伪影响，反而更干净。5000 行档全量 + c-v 可达同级滚动体验，且免掉 §1.2 整套机器；「甜点 ≤500 / 可用 ~5000」包线的量化依据 = JS 层临界线 ① + 编辑分片前提（§3.1）。

### 3.3 全量档的物理红利（虚拟化档没有的）

- ~~**任意速度滚动零白屏（已实测，上屏像素级）**~~ **已撤回（screencast 证伪）**：快拖及以上（≳57 行/步）全量档拖拽期间表体同样 ~100% 白——无未挂载区也白，白的是瓦片未光栅化，不是行未挂载；慢拖满行、松手 ≤600ms 追平，与虚拟化档白法相同（§3.2）。结构上仍成立的部分：DOM 层无未挂载区、滚动零 JS 参与、DOM 采样 0 空白、wheel 惯性段（速度在边界内）满行。
- **Ctrl+F 浏览器查找可用**：虚拟化下未渲染行搜不到（AG Grid 用户长期抱怨点）。
- **a11y 自然阅读序**：无 rebind 乱序，无 aria-rowindex 同步问题（fullrender demo DOM 序天然有序，优于 grid-demo 池化乱序）。
- **打印/复制完整**。
- **autoHeight 回归**（约束 #12 解除）：整表随内容撑开，弹窗/表单内嵌表格不再需要定高容器——小表格场景的高频刚需。
- 树形展开不再需要手工锚点补偿（浏览器原生 scroll anchoring 兜底）。
- **删掉的机器（已按行兑现）**：virtual/rowpool/lead/跳转检测/锚点补偿/键盘协商/行高三档——bug 面与测试面同步缩小。「bug 少」不是靠努力，是靠范围。实测行数账（fullrender demo vs grid-demo，core 全目录，见其 RESULTS「删掉的机器」账）：store.ts **−82**（窗口订阅 + 速度状态机）、virtual.ts **−33**（computeRange）、rowpool→fullbody 删池化/差分规划器 ~160 行换 chunk 调度 + rowId reconcile ~80 行；**signal/command 0 改动**；净 −92 行——行数差不大，**删掉的是全部滚动形态状态机（连续/跳转二分、lead 封顶、跳转阈值这类「必须校准的魔法数」），新增的 chunk/reconcile 无滚动耦合**；onScroll 从「scrollTop.set + 速度喂入 + debounce 清零」缩为**一行**。

### 3.4 幸存与重开

- **core 层 100% 幸存**：signal store、cell 级 === diff、Command→Mutation、selection model、树形扁平投影——全部是数据层，无渲染档假设。canvas spike 已证换渲染器 `diff -r` 零 core 改动；「全量渲染」只是第三个渲染器变体，且是最简单的那个。
- **重开次级决策 #1（`<table>` vs div）**：弃 `<table>` 的主因（调研 §3.1：虚拟化/固定列/合并单元格的结构冲突）随虚拟化进非目标而弱化，`<table>` 的语义/a11y/colspan-rowspan 免费回归。倾向仍 div（CSS 自由度、虚拟化留门、spike 资产复用），但值得记录一次显式评审（§7-3）。

## 4. 市场对照与差异化

### 4.1 此定位不激进：无虚拟化本就是主流默认档

从调研提取：**el-table v1**（`<table>`+sticky、富交互、无虚拟化）、**antd Table**（真实 `<table>`，虚拟滚动 v5.9+ 才作为可选）、**Naive UI**（虚拟滚动长期仅纵向、2.45 才补横向）——主流业务表格的默认档就是全量渲染，虚拟化全部是可选 add-on（el-table-v2 / antd v5.9+ / Naive 2.45 / TanStack 外挂 Virtual）。

**D-2 原文把「万~十万行」定为目标档位，等于把自己钉在 AG Grid 的能力叙事上，而不是业务表格的需求分布上。** 调研 §2 的边界速查（DOM 无虚拟化 ~1k 行）说的也正是：~1k 行是 DOM 全量渲染的舒适区。

### 4.2 该档位的对手与差异化轴

| 对手 | 档位 | 弱点（我们的机会） |
|---|---|---|
| el-table / antd Table / Naive | UI 库附赠表格，全量渲染 | 类型洼地（Element 插槽 scope 无类型 #3233，类型调研 §2.3）、1k 行性能平庸、键盘/a11y 薄弱 |
| TanStack Table | headless 无 UI | 不提供渲染与样式，「小而美开箱」不在其定位 |
| vxe-table | 功能全 | 重；功能堆叠而非架构差异化 |
| AG Grid | 企业档 | 体积/授权/复杂度远超目标场景需要 |

**差异化主轴**：TS 类型体验（类型调研 §1.2 的 10 条验收清单）+ 键盘/a11y 全合规（WAI-ARIA grid，方向 #9 本就采纳）+ 包体/树摇/零依赖 + semver 稳定。

**性能在此档位是卫生因素**：达标即隐形（没人夸 500 行表格流畅），不达标即差评（1k 行卡会被骂）。正确姿势 = 性能预算进 stage-1 验收（用 spike 的 CDP 套件实测），不进卖点叙事。

### 4.3 用户侧价值清单逐条翻译（含各自的坑）

| 用户价值 | 工程承诺 | 里面的坑（所有者猜对了） |
|---|---|---|
| 体验好 | 键盘导航/选区/编辑闭环（#7/#9 幸存） | 键盘表是状态机工程，测试量大 |
| 好看 | 主题系统（design token + CSS 变量层） | 主题 API 一旦发布就是公开 API，返工成本极高 |
| 功能强 | 核心 + 插件（TanStack v9 feature 树摇化先例，调研 §3.2） | API 面 = bug 面；树摇边界必须先行，不能后补 |
| bug 少 | 删虚拟化机器 + 单测契约（两 spike 31+33 个单测的模式） | 「少」来自范围控制，不来自加倍努力 |
| 打包稳 | 零依赖 core + ESM/CJS + semver + d.ts external 策略 | 宿主缺依赖时类型静默退化（类型 QA Q4 已调研） |
| 可拓展 | 渲染器可替换（已双数据点验证）+ 插件边界 | 边界画错 = 未来破坏性重构 |

## 5. 「要么做到极致，要么不做」的落地

### 5.1 极致的操作定义（此档位）

极致 ≠ 功能第二多，而是**该档位里 DX/类型/键盘 a11y/包体/测试/稳定最好**。对照 el-table 必须能一句话说清赢在哪，例如：「类型零标注 + 键盘全操作 + 1000 行 60fps + core 树摇后个位数 kB」。

反命题同样成立：**若说不出这句话，就不该做**——既打不过 UI 库附赠表格的存量惯性，也没有 AG Grid 的能力上限，半吊子没有生态位。

### 5.2 功能强 vs 小核心的张力

解法是结构而非取舍：核心小而稳（渲染 + 状态 + 命令），特性插件化树摇（列设置/导出/列拖拽等首发即可砍进插件）。这与「可拓展」是同一件事的两面。

### 5.3 大表逃生舱三选项（本文核心待决策）

| 选项 | 内容 | 评估 |
|---|---|---|
| **(a) 进非目标，架构留缝（推荐）** | 虚拟化写入非目标；core 无渲染假设（已证）、渲染器接口留缝；spike 代码与优化作业留档作种子 | 符合「要么不做」；成本已由 spike 证明极低（换渲染器零 core 改动）；未来触发时按作业恢复是周级工程 |
| (b) 双档产品 | 默认全量全功能 + 可选「大表模式」（开启 = 显式接受降级契约：定高/无 autoHeight/a11y 限制，文档化） | 风险：两档各自半吊子（违背信条）+ 双倍测试面 + 契约文档的维护负担；仅当内部真有大表需求且不接受分页时才值 |
| (c) 维持 D-2 | 万~十万行虚拟化为默认档 | 与 §2 需求侧证据矛盾；为不存在的用户预付 §1.2 全部代价 |

推荐理由：(a) 的触发条件已经被 §2 论证成立（客群无「滚动即交互」需求）；(b) 作为 (a) 的未来升级路径保留——先不做，需求出现再上，spike 种子不会过期（教训清单即作业手册）。
